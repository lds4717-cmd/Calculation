# 🧠 Mini NPU Simulator (MAC 연산 기반 패턴 판별 계산기)

> **Codyssey Pre-course 필수 미션 - Computer Science**  
> AI 전용 하드웨어(NPU)의 핵심 연산인 **MAC(Multiply-Accumulate)** 원리를 외부 벡터화 라이브러리(NumPy 등) 없이 순수 Python 표준 문법만으로 구현하고, 데이터 크기($3\times3 \sim 25\times25$)에 따른 시간 복잡도($O(N^2)$)와 허용오차($\epsilon$) 기반 수치 비교 정책을 검증하는 콘솔 시뮬레이터입니다.

---

## 🚀 1. 실행 방법

### 1) 개발 환경 및 제약 조건
- **Python 버전**: Python 3.8 이상 (권장: Python 3.10+)
- **사용 라이브러리**: Python 표준 라이브러리(`json`, `os`, `time`)만 사용 (NumPy, pandas 등 외부 라이브러리 미사용)
- **데이터 파일 위치**: 프로젝트 루트 디렉토리 내 `./data.json`

### 2) 실행 절차 및 모드 선택
```bash
# 1. 프로젝트 루트 디렉토리 이동
cd codyssey

# 2. 시뮬레이터 실행 (OS 환경에 따라 python 또는 py 사용)
python main.py
```

프로그램 실행 후 콘솔 안내에 따라 모드를 선택합니다.
- **`1`번 (사용자 입력 모드 - $3\times3$)**: $3\times3$ 크기의 필터 2개(A, B)와 입력 패턴 1개를 공백으로 구분해 한 줄씩 직접 입력하여 두 필터의 MAC 점수, 평균 연산 시간(ms), 판정 결과(`A`/`B`/`판정 불가`)를 확인합니다.
- **`2`번 (`data.json` 분석 모드)**: 프로젝트 루트의 `data.json`에서 $5\times5$, $13\times13$, $25\times25$ 필터와 테스트 패턴 6종을 일괄 로드하여 라벨 정규화, 케이스별 `PASS`/`FAIL` 판정, 크기별 성능 분석표($3\times3$ 포함), 최종 결과 요약을 출력합니다.

## ⚙️ 2. 구현 요약

### 1) MAC(Multiply-Accumulate) 연산 구현 개요
- 크기 $N \times N$의 2차원 입력 패턴 $P$와 필터 $F$를 이중 반복문(`for`)으로 순회하며, 동일 위치 $(i, j)$의 원소끼리 곱하고 누적합을 계산합니다.
$$\text{Score} = \sum_{i=0}^{N-1} \sum_{j=0}^{N-1} P[i][j] \times F[i][j]$$
- 벡터화 라이브러리 없이 순수 반복문으로 구현하여 $N \times N$ 행렬의 실제 연산 횟수($N^2$)와 실행 시간 증가 추이를 직접 계측할 수 있도록 설계했습니다.

### 2) 라벨 정규화(Label Normalization) 방식
- `data.json` 내부에 혼용된 라벨 표기(`'+'`, `'cross'`, `'x'`, `'X'`)로 인한 비교 오류를 방지하기 위해, 데이터 로드 직후 프로그램 내부 표준 라벨인 **`Cross`**와 **`X`**로 일괄 정규화합니다.
  - 필터 키 정규화: `'cross'` $\rightarrow$ `Cross`, `'x'` $\rightarrow$ `X`
  - 정답(`expected`) 정규화: `'+'` $\rightarrow$ `Cross`, `'x'` $\rightarrow$ `X`
- 모든 콘솔 판정 출력과 `PASS`/`FAIL` 검증은 정규화된 표준 라벨(`Cross`, `X`, `UNDECIDED`)을 기준으로 수행합니다.

### 3) 동점 및 부동소수점 비교 정책 ($\epsilon$ 기반)
- 실수형 가중치 연산 시 발생하는 IEEE 754 부동소수점 미세 오차(`0.9` vs `0.8999999999999999` 등)로 인해 사실상 동일한 점수가 한쪽으로 편향 판정되는 문제를 방지하기 위해 허용오차($\epsilon = 10^{-9}$) 기반 비교 정책을 적용했습니다.
  - $\vert{} \text{Score}_A - \text{Score}_B \vert{} < 10^{-9}$ 인 경우: **`UNDECIDED` (판정 불가)** 처리
  - $\text{Score}_A - \text{Score}_B \ge 10^{-9}$ 인 경우: **`A` (`Cross`)** 판정
  - $\text{Score}_B - \text{Score}_A \ge 10^{-9}$ 인 경우: **`B` (`X`)** 판정

### 4) 입력 검증 및 예외 방어 처리
- **모드 1 (사용자 입력)**: 행/열 개수 불일치(3개 미만·초과), 공백·빈 입력, 숫자 변환 실패(`ValueError`) 발생 시 프로그램이 비정상 종료되지 않고 오류 안내 문구를 출력한 뒤 해당 줄부터 재입력을 유도합니다.
- **모드 2 (`data.json` 스키마 검증)**: 패턴 키(`size_{N}_{idx}`)에서 추출한 크기 $N$과 실제 2차원 배열의 행/열 크기가 일치하지 않을 경우, 전체 실행을 중단하지 않고 해당 케이스만 `FAIL` 처리하고 불일치 사유를 리포트에 기록합니다.

## 📊 3. 결과 리포트 (성능 분석 및 실패 원인 분석)

### 1) 크기별 MAC 연산 성능 분석표 (10회 반복 평균)
> 파일 I/O 및 콘솔 출력 시간을 제외하고 순수 `mac_operation()` 함수 호출 구간만 `time.perf_counter()`로 10회 반복 측정한 실제 실행 결과입니다.

| 패턴 크기 ($N \times N$) | 연산 횟수 ($N^2$) | 평균 연산 시간 (ms) | $3\times3$ 대비 연산 횟수 배율 |
| :---: | :---: | :---: | :---: |
| **$3 \times 3$** | 9 | `0.0030 ms` | $1.00\times$ |
| **$5 \times 5$** | 25 | `0.0027 ms` | $2.78\times$ |
| **$13 \times 13$** | 169 | `0.0141 ms` | $18.78\times$ |
| **$25 \times 25$** | 625 | `0.0664 ms` | $69.44\times$ |

### 2) 시간 복잡도 $O(N^2)$ 분석 및 성능 표 해석
- **이론적 근거 ($O(N^2)$)**: 가로 $N$, 세로 $N$ 크기의 2차원 배열에서 모든 격자 원소를 한 번씩 순회하며 곱셈 1회와 덧셈 1회를 수행합니다. 따라서 입력 배열의 한 변 길이가 $N$일 때 총 기본 연산 횟수는 $N \times N = N^2$에 정확히 비례하며, 알고리즘의 시간 복잡도는 **$O(N^2)$**입니다.
- **실측 데이터와 연산 횟수의 연결**: 위 성능 분석표에서 $3\times3$(9회)과 $5\times5$(25회)는 연산량이 매우 작아 OS 스케줄링 및 타이머 오버헤드 영향으로 유사한 수준(`0.0030 ms` vs `0.0027 ms`)을 보입니다. 그러나 연산량이 본격적으로 커지는 $5\times5$(25회) $\rightarrow$ $13\times13$(169회, $6.76$배 증가) $\rightarrow$ $25\times25$(625회, $25$배 증가) 구간을 보면, 실측 평균 연산 시간 역시 `0.0027 ms` $\rightarrow$ `0.0141 ms`($5.22$배 증가) $\rightarrow$ `0.0664 ms`($24.59$배 증가)로 연산 횟수($N^2$) 증가율과 거의 정확히 비례하여 **$O(N^2)$** 복잡도를 실증합니다.
- **CPU 직렬 처리의 한계와 NPU의 필요성**: 현재 구현된 Python 반복문 방식은 CPU가 625번의 MAC 연산을 순서대로 하나씩 처리하는 직렬 구조이므로, 입력 해상도가 수백$\times$수백 단위로 커지면 연산 시간이 제곱($N^2$) 속도로 급증하여 실시간 처리가 어려워집니다. 이를 극복하기 위해 다수의 MAC 연산기를 하드웨어 격자로 배치해 수천 개의 곱셈·누적 연산을 한 클럭에 동시 수행(병렬 처리)하는 **NPU(Neural Processing Unit)** 아키텍처가 필수적임을 확인할 수 있습니다.

### 3) 실패(FAIL) 케이스 원인 분석 (총 6개 테스트 중 3개 통과 / 3개 실패)
> `data.json` 전체 6개 테스트 케이스 수행 결과 발생한 실패 케이스 3건의 원인을 **데이터/스키마 문제 vs 로직 문제 vs 수치 비교 문제**로 분리해 진단한 결과입니다.

1. **부동소수점 오차 및 허용오차($\epsilon$) 동점 정책에 의한 실패 3건 (`size_5_1`, `size_13_2`, `size_25_1`)**
   - **현상**:
     - `size_5_1`: `Cross` 점수 `0.9` vs `X` 점수 `0.8999999999999999` (차이 $1.11 \times 10^{-16}$) $\rightarrow$ 판정 `UNDECIDED` (`expected: X`)
     - `size_13_2`: `Cross` 점수 `7.499999999999997` vs `X` 점수 `7.5` (차이 $2.66 \times 10^{-15}$) $\rightarrow$ 판정 `UNDECIDED` (`expected: Cross`)
     - `size_25_1`: `Cross` 점수 `4.9` vs `X` 점수 `4.899999999999999` (차이 $8.88 \times 10^{-16}$) $\rightarrow$ 판정 `UNDECIDED` (`expected: X`)
   - **원인 진단 (수치 비교 및 동점 정책 문제)**: 세 케이스 모두 두 필터의 수학적 실제 합계는 완전히 동일하지만, 컴퓨터 내부의 IEEE 754 부동소수점 실수 연산 과정에서 $10^{-15} \sim 10^{-16}$ 수준의 미세한 표현 오차가 발생했습니다. 만약 단순 부등호(`score_cross > score_x`)로 판정했다면 `size_13_2`는 `X`로 오판정되고 `size_5_1`, `size_25_1`은 우연히 `Cross`로 판정되는 등 신뢰할 수 없는 결과가 나옵니다. 허용오차 정책($\vert{}\text{Score}_A - \text{Score}_B\vert{} < 10^{-9}$)을 적용함에 따라 세 케이스 모두 유의미한 점수 차이가 없는 동점 상태(`UNDECIDED`)로 정확히 걸러냈으며, 이에 따라 특정 라벨(`Cross` 또는 `X`)을 기대한 `expected` 기준과 불일치하여 정상적으로 `FAIL` 처리되었습니다.
2. **데이터/스키마 문제 및 연산 로직 문제의 정상 통과 검증 (`size_5_2`, `size_13_1`, `size_25_2`)**
   - **원인 분리**: `data.json`의 `expected` 표기(`'+'`, `'x'`)와 필터 키(`'cross'`, `'x'`)는 입력 계층의 라벨 정규화 파이프라인(`Cross`, `X` 통일)을 통해 스키마 불일치 없이 완벽히 매핑되었으며, 모든 패턴과 필터의 배열 크기($5\times5$, $13\times13$, $25\times25$) 또한 정상 일치했습니다. 그 결과 점수 차이가 명확한 `size_5_2`(`8.9` vs `0.1`), `size_13_1`(`0.3` vs `14.700000000000008`), `size_25_2`(`52.9` vs `0.1`) 세 케이스는 모두 `PASS`를 기록하여 핵심 MAC 연산 로직과 정규화 로직에 결함이 없음을 검증했습니다.
